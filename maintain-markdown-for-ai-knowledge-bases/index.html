S1.1 · Opening

Maintain markdown for AI knowledge bases

AI collapsed the cost of writing documentation and raised the cost of verifying it. The work moved — and the verifying half is nobody else's job.

Han Che

Scroll

S2.1 · What a markdown file is

One file at the centre, three things we ask of it

A text file with nothing mechanical underneath. What matters is how and when it is consumed: as context, as knowledge, as instruction.

Speaker notes

Start by leveling the room: a markdown file is just a plain text file. There is no runtime engine, no compiler, no relational database, and nothing mechanical underneath. It is inert characters on disk.

What gives it weight is purely how and when an AI agent consumes it: as ambient context (like AGENTS.md or CLAUDE.md that sets the ground rules), as institutional knowledge (a wiki or runbook fetched when needed), or as an operational instruction (a skill or prompt executed step by step). Notice that small frontmatter block at the top — we will come back to that.

S3.1 · Why this was always hard

Two curves, and the point where they cross

Effort over time, anchored at the day the document reached production. Creation collapses with AI. Verification climbs with volume.

Speaker notes

Before day zero — when the document reaches production — authoring was the hard part. Writing by hand was slow and expensive, so verification was quiet because volume was strictly capped by human typing speed.

AI completely inverted that curve: creation effort collapsed to near zero. Anyone and any script can generate fifty pages of documentation in seconds. But verification effort does not stay flat — it climbs with volume.

This crossover is the core thesis of the talk: where the work moved. The bottleneck is no longer writing; it is proving what was written is still true.

S4.1 · Where the effort goes

Machines check structure. Humans check truth.

What a machine can check, what AI can help with, and what only a human can check — drawn to proportion, because the proportions are the argument.

Speaker notes

AI is an accelerator here, not a solution. It will run the fact-check, chase the hard numbers, flag the paragraph that smells wrong — and every answer it hands back is itself a claim that still needs checking. That is why its region is labelled with a question mark: whatever AI takes on lands back in one of the other two regions.

Callback: the freelancer with amnesia. Brilliant, fast, and shows up every morning having forgotten everything — the knowledge base is the only memory it has, and it believes whatever the files say. A machine can prove the files still parse; only a human can know whether that memory is still true.

S5.1 · Three passes over one file

The machine pass resolves cleanly

One real frontmatter block, assessed mechanically. Syntax parses, URLs resolve, dates check out. This is what mechanical checking is genuinely good at.

Machine pass Resolves cleanly
  • ✓ Syntax: valid YAML frontmatter delimiter & structure
  • ✓ Resource: https://internal.corp/spec/v2 reachable (HTTP 200)
  • ✓ Staleness: 2026-06-01T00:00:00+00:00 parses with explicit UTC offset

Machine checking proves the file is mechanically intact. It cannot tell you whether the content is true.

Speaker notes

Point out that OKF only requires type. The staleness date is optional. The machine pass passes not because the format demanded it, but because our own lint rule checked for it.

The machine checks syntax, parses dates, and verifies that the link resolves. Everything it was asked to check resolves cleanly. Mechanical checking is the settled, easy part of the talk.

S5.2 · Three passes over one file

The AI pass returns a claim

The same block, read by an AI. The answer comes back amber: rapid, insightful, and itself in need of checking.

1. Machine pass ✓ Resolved cleanly
AI pass Needs verification

Observation Compared document.md against linked spec v2. Section 4.2 of the spec updated error responses from HTTP 400 to 409 Conflict.

Proposal Recommend updating the guide and advancing stale_after by 30 days.

? Accelerator, not resolution: this finding is itself a claim requiring verification.

Speaker notes

Now an AI inspects the file. It ingested the 14-page spec and caught a discrepancy in section 4.2: error code 400 changed to 409. It proposes a documentation update and moving the date.

Notice what happened: AI gave us an answer, but that answer is not a resolution. It is a new claim. Is 409 an unreleased draft? Did the API actually deploy? Whatever AI takes on lands right back in need of checking.

S5.3 · Three passes over one file

The human pass stays unresolved

Is it still true? Does the reference point at the right content? This pass deliberately does not resolve on screen.

1. Machine pass ✓ Resolved cleanly
2. AI pass ⚠ Claim returned (needs check)
Human pass Open · Unresolved
? Is internal.corp/spec/v2 still the authority, or did the team switch to event-driven v3?
? Is HTTP 409 intentional or an unreleased staging draft?
? Should stale_after move forward, or does this document need complete retirement?

This question stays open on screen. The machine checked the syntax; the AI drafted a clue; only a human can answer whether it is true.

Speaker notes

This is the load-bearing beat of section 5: the human pass deliberately stays unresolved on screen.

No machine test and no AI summary can sign this document. Only the human operator with domain context can determine if the service migrated or if the staleness date should move. That is why this beat ends with open questions — the talk does not resolve them for you.

S6.1 · OKF

Who supplies which field

The same frontmatter block, grown to its full field set. The machine-signed field and the human-signed field sit adjacent with identical structure.

Read the public OKF v0.2 specification ↗ Click any field above to inspect its supplier

Speaker notes

Don't lecture on the schema. The power of this slide is the adjacent comparison: generated and verified have identical shapes — { by, at }. One is signed by a model, the other is signed by a human.

Who supplies each field does the argument's work on its own. The human sets the authority and review deadline; the machine executes and logs its timestamp; the human verifies.

S7.1 · markdown-harness

The signal is in the file; the instruction has to come from you

The file stores the signal — stale_after. The machine does not invent policy; the operator writes the instruction.

Operator rule markdown-harness config

Configured instruction:

“If the current date is past stale_after, notify the user that this document is stale and propose opening a refresh ticket with the maintainer.”

→ The signal: parsed directly from the OKF metadata in the file.

→ The instruction: authored by the team to match your workflow.

Speaker notes

Set up the demo before touching the terminal. The signal is passive — it sits inert in the file until someone asks a question.

And when the tool fires, what does it say? It does not say what a vendor programmed it to say. It says whatever sentence the operator configured. In production, that means proposing a ticket. (In our live demo in a moment, you'll see a slightly more unmistakable signal.)
