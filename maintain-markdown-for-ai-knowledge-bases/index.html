S2.1 · Markdown in AI Workflows

Markdown files in the era of AI

A plain text file with nothing mechanical underneath. What matters is how and when it is consumed: as context, as knowledge, as instruction.

Speaker notes

Start by leveling the room: a markdown file is just a plain text file. There is no runtime engine, no compiler, no relational database, and nothing mechanical underneath. It is inert characters on disk.

What gives it weight is purely how and when an AI agent consumes it: as ambient context (like AGENTS.md or CLAUDE.md that sets the ground rules), as institutional knowledge (a wiki or runbook fetched when needed), or as an operational instruction (a skill or prompt executed step by step). Notice that small frontmatter block at the top — we will come back to that.

S3.1 · The Maintenance Gap

Maintenance effort is rarely scheduled — until documentation fails

Effort over time, anchored at the day the document reached production. Creation collapses with AI. Verification climbs with volume.

Speaker notes

Before day zero — when the document reaches production — authoring was the hard part. Writing by hand was slow and expensive, so verification was quiet because volume was strictly capped by human typing speed.

AI completely inverted that curve: creation effort collapsed to near zero. Anyone and any script can generate fifty pages of documentation in seconds. But verification effort does not stay flat — it climbs with volume.

This crossover is the core thesis of the talk: where the work moved. The bottleneck is no longer writing; it is proving what was written is still true.

S4.1 · Verification Boundaries

Where documentation verification actually happens

Dividing verification into three boundaries: what a machine automates, what AI accelerates, and what only a human can decide. Drawn to proportion, because the proportions are the argument.

Speaker notes

AI is an accelerator here, not a solution. It will run the fact-check, chase the hard numbers, flag the paragraph that smells wrong — and every answer it hands back is itself a claim that still needs checking. That is why its region is labelled with a question mark: whatever AI takes on lands back in one of the other two regions.

Callback: the freelancer with amnesia. Brilliant, fast, and shows up every morning having forgotten everything — the knowledge base is the only memory it has, and it believes whatever the files say. A machine can prove the files still parse; only a human can know whether that memory is still true.

S5.1 · Pass 1: Machine Verification

Where the effort goes: Pass 1 — What the machine verifies

Syntactic and structural checks that run deterministically in milliseconds without an LLM. Syntax parses, URLs resolve, and ISO dates validate.

Machine pass Resolves cleanly
  • ✓ Syntax: valid YAML frontmatter delimiter (---) & structure
  • ✓ Resource: https://intranet.example.com/people-ops/handbook reachable (HTTP 200)
  • ✓ Staleness: 2025-07-01T00:00:00Z parses with valid ISO timestamp

Machine checking proves the file is mechanically intact. It cannot tell you whether the onboarding workflow is still true.

Speaker notes

Point out that OKF only requires type. The staleness date is optional. The machine pass passes not because the format demanded it, but because our own lint rule checked for it.

The machine checks syntax, parses dates, and verifies that the link resolves. Everything it was asked to check resolves cleanly. Mechanical checking is the settled, easy part of the talk.

S5.2 · Pass 2: AI Assistance

Where the effort goes: Pass 2 — What AI can check

Cross-referencing prose against source handbooks to flag discrepancies for human review. The answer comes back amber: rapid, insightful, and itself in need of checking.

1. Machine pass ✓ Resolved cleanly
AI pass Needs verification

Observation Compared onboarding.md against linked People Ops handbook. Section 4 of the handbook updated equipment lead times from 5 working days to 7 working days.

Proposal Recommend updating line 15 and proposing a verification review with People Ops.

? Accelerator, not resolution: this finding is itself a claim requiring verification.

Speaker notes

Now an AI inspects the file. It ingested the linked handbook and caught a discrepancy: equipment lead time changed from 5 to 7 days. It proposes a documentation update and flagging for review.

Notice what happened: AI gave us an answer, but that answer is not a resolution. It is a new claim. Has IT actually instituted the 7-day policy? Is the intranet page up to date? Whatever AI takes on lands right back in need of checking.

S5.3 · Pass 3: Human Ground Truth

Where the effort goes: Pass 3 — The human judgment that remains

Is the policy still in force? Is the owner correct? Ground truth that no machine or model can know. This pass deliberately stays open on screen.

1. Machine pass ✓ Resolved cleanly
2. AI pass ⚠ Claim returned (needs check)
Human pass Open · Unresolved
? Does the buddy coffee on day one still match team practice?
? Does People Ops still close payroll on the 20th?
? Is @m.okonkwo still the active maintainer for onboarding?

This question stays open on screen. The machine checked the syntax; the AI drafted a clue; only a human can answer whether it is true.

Speaker notes

This is the load-bearing beat of section 5: the human pass deliberately stays unresolved on screen.

No machine test and no AI summary can sign this document. Only the human operator with domain context can determine if the policy changed or if the staleness date should move. That is why this beat ends with open questions — the talk does not resolve them for you.

S7.1 · Operator Governance

The signal is in the file; the instruction comes from you

The file stores the signal — stale_after. The machine does not invent policy; the operator writes the instruction.

Operator rule markdown-harness config

Configured instruction:

“If the current date is past stale_after, notify the user that this document is stale and propose opening a refresh ticket or verifying with People Ops.”

→ The signal: parsed directly from the OKF metadata in the file.

→ The instruction: authored by the team to match your workflow.

Speaker notes

Set up the demo before touching the terminal. The signal is passive — it sits inert in the file until someone asks a question.

And when the tool fires, what does it say? It does not say what a vendor programmed it to say. It says whatever sentence the operator configured. In production, that means proposing a ticket or verifying with People Ops.

✓ Guaranteed Operator Instruction

The team's instruction is deterministically injected every time. The model is forced to adopt a defensive posture before anyone follows an expired playbook.

Speaker notes

Rescue slide: In a standard run, do not dwell here — step directly into your live terminal session to show the contrast in real time.

If the live demo fails (network drop, tool crash, LLM latency), stay on this slide. Point out the two legs: on the left, an unassisted agent might mention the date, but it doesn't enforce team policy. On the right, markdown-harness intercepts the file read, notes that stale_after has elapsed, and forces Claude to adopt the team's defensive posture: proposing a ticket or checking with People Ops before taking action.

S9.1 · Conclusion

The verifying half is nobody else's job

The talk ends on the image it argued from. Machines check structure; AI accelerates; the human region is where the work moved.

Speaker notes

Land the conclusion cleanly. The human region is not an unfortunate residue we haven't figured out how to automate yet. It is the real work of knowledge maintenance.

Machines check structure. AI accelerates drafting and fact-checking. But only humans decide whether a document remains true, whether an owner is still accountable, and whether policy matches reality.
