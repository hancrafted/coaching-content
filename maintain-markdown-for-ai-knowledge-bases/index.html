Intro

Maintain markdown for AI knowledge bases

AI collapsed the cost of writing documentation and raised the cost of verifying it. The work moved — and the verifying half is nobody else's job.

Han Che

Speaker note

Markdown files now sit at the centre of every AI workflow. When those workflows quietly degrade — wrong answers, drifting behaviour, confident nonsense — people blame the model or the prompt. Usually the culprit is a markdown file nobody has maintained. AI is not a solution; it consumes these files and treats them as plain truth.

This is for anyone whose work touches an AI workflow, not just engineers. If you write documentation, own a process, or maintain a handbook, these files are already reading over your shoulder.

Markdown files in the era of AI

A plain text file with nothing mechanical underneath. What matters is how and when it is consumed: as knowledge, as instructions, as memory — and whether the agent pays for it on every turn or only when it reaches for it.

Three of the six context types in Osmani, Saboo & Kartakis, The New SDLC with Vibe Coding (Google, May 2026), fig. 4 — static versus dynamic context.

Speaker note

Markdown won because it lets you enrich a file with context, not just words. Heading, bold, list, checkbox — a second layer of structure over otherwise unstructured text, with no special skills needed to add it.

Three places you already meet it: knowledge — the wiki, increasingly authored and maintained by an agent rather than a person; instructions — a repeated workflow packaged as a skill; memory — what an agent needs to know about your project at all times, e.g. AGENTS.md or CLAUDE.md.

The split that matters is when each one is paid for. Memory is static context: always loaded, every interaction, whether or not it is relevant — so length is a budget. Knowledge and instructions are dynamic: retrieved on demand, or loaded when a task matches the skill's description. That boundary is a first-class architectural decision, and the paper argues it should be reviewed and versioned like any other configuration.

At moderate scale — roughly a hundred sources, a few hundred pages — an index file plus linked markdown works better than expected and needs no embedding-based retrieval infrastructure at all. Karpathy's LLM-wiki gist says exactly this. Obsidian is the everyday version: the agent edits on one side, you browse the graph on the other.

Volume Outruns Review

Maintenance effort is rarely scheduled — until documentation fails

Two different things get harder. On a single document, maintenance effort decays while drift keeps climbing. Across a corpus, the maintenance surface grows faster than the file count.

Speaker note

The chart is not the point — the gap is. Creating a document was always the cheap half, even before AI. The hard half was always keeping it alive and keeping it trustworthy.

AI did not invent that problem, it amplified it. An agent reading an unverified file assumes it is current and never tells you otherwise.

And nobody schedules maintenance. It gets treated the way technical debt gets treated — real, accumulating, never on anyone’s plan — unless someone actually owns the files. That is true of a handful of AGENTS.md files, and it is true of a thousand-file repository where documents start contradicting each other.

Information architecture was always the answer to this — organising a knowledge base so it does not grow organically and explode in maintenance cost. That problem predates AI entirely.

If pushed outside the source: Karpathy’s LLM-wiki gist argues the same shift independently — the wiki is written and read by an agent, and the human’s job moves from authoring to curating and verifying. Already linked on the Knowledge card in section 2.

Verification Boundaries

Where verification happens

Dividing verification into three boundaries: what a machine automates, what AI accelerates, and what only a human can decide. Drawn to proportion, because the proportions are the argument.

Speaker note

Machine verification is deterministic — same input, same output, always. It is cheap and fast, which means it should run constantly, and the AI should be running it too as a self-check loop.

Human verification is semantic. Is this fact still true? Is the linked source still the right one? Does it still say what we claimed it says? No algorithm catches that.

AI sits in the overlap, and it is genuinely new — the first tool that works with meaning rather than structure. That is why this region is unsettled: people are still working out what belongs in it. My hypothesis is that AI does the grunt work. Summarising, researching, orienting you, drafting the executive summary. What it does not do is deliver the verdict.

Handing an AI the judgment that a document is still true and then walking away is the dangerous path — and it is the first thing most people reach for.

Machine Verification

What the machine verifies

Syntactic and structural checks that run deterministically in milliseconds without an LLM. Syntax parses, URI format is validated, and ISO dates validate.

Machine check Resolves cleanly
  • ✓ Syntax: valid YAML frontmatter delimiter (---) & structure
  • ✓ Resource: present and well-formed URI (https://intranet.example.com/people-ops/handbook#onboarding)
  • ✓ Staleness: 2026-07-01T00:00:00Z parses with valid ISO timestamp

Machine checking proves the file is mechanically intact. It cannot tell you whether the onboarding workflow is still true.

Speaker note

This is the metadata block at the top of the file. Not the document — the description of the document. Type, title, the source it came from, and a date somebody chose, saying this goes out of date after the first of July.

A machine confirms the block parses, the fields exist, the date is a real date, the link is well-formed. Milliseconds, offline, no model involved. You can go further into the body if you want: every document starts with a heading, sections appear in the right order. All of it structural.

Every one of those checks is about shape. None of them is about truth.

The date parses — nobody checked whether it was ever right. The link is well-formed — and if that handbook page was rewritten, or the content moved somewhere else under a URL that still resolves, the check still passes. A link that still works is not a link that still says what you claimed.

The machine proves the file is mechanically intact. It cannot tell you whether the onboarding workflow is still true.

Hold in reserve. OKF only requires type. The staleness date is optional — this check passes because our own rule asked for it, not because the format demanded it. And if an engineer raises cost: structural checks on the body can get expensive at ten thousand documents, depending on the matching. Neither belongs in the main narration.

AI Acceleration

What AI accelerates

Cross-referencing prose against source handbooks to flag discrepancies for human review. The answer comes back rapid, insightful, and itself in need of checking.

Machine check ✓ Resolved cleanly
fast and cheap to re-run
AI recommendation Needs verification

Observation Compared onboarding.md against linked People Ops handbook. Section 4 of the handbook updated equipment lead times from 5 working days to 7 working days.

Proposal Recommend updating line 15 and proposing a verification review with People Ops.

? Automated recommendation, not verified ground truth: this finding requires human confirmation.

Speaker note

Now an AI inspects the file. It ingested the linked handbook and caught a discrepancy: equipment lead time changed from 5 to 7 days. It proposes a documentation update and flagging for review.

Notice what happened: AI gave us an answer, but that answer is not a resolution. It is a new claim. Has IT actually instituted the 7-day policy? Is the intranet page up to date? Whatever AI takes on lands right back in need of checking.

Human Judgment

What remains human

Is the policy still in force? Is the owner correct? Ground truth that no machine or model can know. This judgment stays open on screen.

Machine check ✓ Resolved cleanly
AI recommendation ⚠ Discrepancy flagged (needs check)
selective re-check, not a full re-run
Human judgment Open · Unresolved

Onboarding playbook verification (this document)

? Does the buddy coffee on day one still match team practice?
? Does People Ops still close payroll on the 20th?
? Is @m.okonkwo still the active maintainer for onboarding?

Portable truth verification (your documentation)

? Reality check: Is the policy described here still true in production?
? Workflow alignment: Does this still reflect how people actually work day to day?
? Authority: Is the person or team named still the right authority to verify it?

This judgment stays open on screen. The machine checked the syntax; AI drafted a recommendation; only a human establishes ground truth.

Speaker note

This is the load-bearing beat of section 5: the human pass deliberately stays unresolved on screen.

No machine test and no AI summary can sign this document. Only the human operator with domain context can determine if the policy changed or if the staleness date should move. That is why this beat ends with open questions — the talk does not resolve them for you.

Open Knowledge Format

OKF standardises the signal

A set of frontmatter fields to govern markdown files. The machine-signed field and the human-signed field sit adjacent with identical structure.

Read the public OKF v0.2 specification ↗
Speaker note

Don't lecture on the schema. The power of this slide is the adjacent comparison: generated and verified have identical shapes — { by, at }. One is signed by Opus 5, the other is signed by a human.

Who supplies each field does the argument's work on its own. The human sets the authority and review deadline; the machine executes and logs its timestamp; the human verifies.

Operator Governance

The signal is in the file; the instruction comes from you

The file stores the signal — stale_after. The machine does not invent policy; the operator writes the instruction.

Operator rule markdown-harness config

Configured instruction:

“If the current date is past stale_after, notify the user that this document is stale and propose opening a refresh ticket or verifying with People Ops.”

→ The signal: parsed directly from the OKF metadata in the file.

→ The instruction: authored by the team to match your workflow.

Speaker note

Set up the demo before touching the terminal. The signal is passive — it sits inert in the file until someone asks a question.

And when the tool fires, what does it say? It does not say what a vendor programmed it to say. It says whatever sentence the operator configured. In production, that means proposing a ticket or verifying with People Ops.

Conclusion

The verifying half is yours

The talk ends on the image it argued from. Machines check structure; AI accelerates; the human region is where the work moved.

Speaker note

Land the conclusion cleanly. The human region is not an unfortunate residue we haven't figured out how to automate yet. It is the real work of knowledge maintenance.

Machines check structure. AI accelerates drafting and fact-checking. But only humans decide whether a document remains true, whether an owner is still accountable, and whether policy matches reality.
